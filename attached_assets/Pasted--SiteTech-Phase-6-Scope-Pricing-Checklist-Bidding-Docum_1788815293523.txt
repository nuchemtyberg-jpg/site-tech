# SiteTech — Phase 6: Scope & Pricing Checklist + Bidding Document Foundation

We are continuing development of the SiteTech construction management platform.

Existing functionality includes:

- Customers / Companies
- Multiple Customer Contacts
- Projects
- Opportunities / RFPs
- Bidding / Opportunity Pipeline
- Opportunity Contacts
- Todos / My Work
- Workflow Automation
- Notifications / Email
- Communications
- Activity / Audit History
- User permissions

The next phase is:

# SCOPE & PRICING CHECKLIST

The purpose of this phase is to define exactly what work SiteTech is being asked to price for each Opportunity.

This information will eventually feed:

Opportunity
→ Scope
→ Takeoff
→ Estimate
→ Proposal

Do NOT build the full Takeoff or Estimating engine yet.

Also establish the document architecture described below so bidding documents can follow an Opportunity into the eventual Project.

==================================================
1. CORE CONCEPT
==================================================

An Opportunity represents a potential job.

The Scope & Pricing Checklist represents the work SiteTech intends to evaluate and potentially price for that Opportunity.

Example:

Opportunity:
123 Main Street

Scope:

☑ Site Clearing
☑ Demolition
☑ Excavation
☑ Foundation Excavation
☑ Storm Sewer
☑ Sanitary Sewer
☐ Water
☑ Grading
☑ SOE
☐ Paving

The checklist must be more than a simple checkbox.

Each scope item should eventually be capable of connecting to:

- Takeoff
- Estimate
- Proposal

Do not implement those future systems yet, but design the database so they can connect cleanly later.

==================================================
2. SCOPE ITEM DATA MODEL
==================================================

Create a reusable Scope Item structure.

Conceptually:

5. INCLUDED / EXCLUDED
==================================================

The user should be able to clearly identify:

Included Scope

and

Excluded Scope

Example:

Foundation excavation

==================================================
6. SCOPE ITEM NOTES
==================================================

Each Scope Item should support notes.

Example:

Excavation

Notes:
Includes excavation to proposed subgrade. Rock excavation excluded.

These notes are specific to this Opportunity.

Do not modify the master Scope Item description when a user adds Opportunity-specific notes.

==================================================
7. SCOPE DESCRIPTION
==================================================

Each Scope Item should support an optional description.

Example:

Storm Sewer

Description:
Complete storm drainage system shown on civil drawings.

Keep the master scope description separate from Opportunity-specific notes.

==================================================
38. IMPORTANT — DO NOT CONFUSE SCOPE WITH ESTIMATE
==================================================

Scope answers:

"What work are we pricing?"

Estimate answers:

"How much will that work cost?"

Takeoff answers:

"How much quantity is involved?"

Proposal answers:

"What are we offering the customer?"

Keep these concepts separate.

==================================================
47. COMPLETION CRITERIA
==================================================

Phase 6 is complete when:

- Opportunity has a functional Scope Checklist.
- Scope Items are organized by category.
- Users can mark Included / Excluded / Needs Clarification / Not Reviewed.
- Scope-specific notes work.
- Custom Scope Items work.
- Scope Templates are supported or architected cleanly.
- Scope Items have stable IDs for future Takeoff relationships.
- Scope-related Todos use the existing Todo system.
- Scope Activity uses the existing Activity system.
- Opportunities have a functional document area.
- Documents have useful categories.
- Document versions are preserved.
- Superseded documents remain accessible.
- Documents can eventually follow an Opportunity into a Project without unnecessary physical duplication.
- Existing Customer/Project/Opportunity document architecture is preserved.
- Mobile experience is clean.
- Existing SiteTech functionality remains intact.

==================================================
FINAL ARCHITECTURAL PRINCIPLE
==================================================

Build this as a connected construction workflow, not isolated features.

The long-term chain is:

CUSTOMER
↓
OPPORTUNITY
↓
DOCUMENTS + SCOPE
↓
TAKEOFF
↓
ESTIMATE
↓
PROPOSAL
↓
AWARDED
↓
PROJECT
↓
FIELD / PROJECT MANAGEMENT

The information entered during bidding should follow the job into the Project.

Avoid duplicate data entry wherever possible.

Avoid duplicate physical files wherever possible.

Maintain a clear source of truth for Customers, Contacts, Documents, Scope, Todos, Communications and Activity.

Before making database changes, inspect the existing SiteTech document/file architecture and reuse it rather than creating a second document management system.
