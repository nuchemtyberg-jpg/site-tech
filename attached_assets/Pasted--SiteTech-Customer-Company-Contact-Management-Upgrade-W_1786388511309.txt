# SiteTech — Customer / Company & Contact Management Upgrade

We already have an existing **Customers** module in SiteTech.

Current functionality includes:

* Customer list
* Create Customer form
* Customer detail page
* Customer contact information
* Customer company name
* Customer address
* Customer notes
* Projects linked to customers
* Communications linked to customers
* Existing customer search
* Existing customer deletion
* Existing Project → Customer relationships

We now need to upgrade this architecture so that a **Customer represents a company/organization**, and each Customer can have **multiple individual Contacts**.

This work must preserve all existing customer, project, and communication data.

---

# PRIMARY GOAL

Change the customer architecture from essentially:

Customer = Contact + Company

to:

Customer / Company
→ Many Contacts
→ Many Projects
→ Many Communications
→ Future Opportunities / RFPs
→ Future Proposals / Contracts

Do not create a new parallel customer system.

Extend and migrate the existing Customer system.

---

# 1. EXISTING APPLICATION REVIEW

Before making changes, inspect:

* Existing Customer database schema
* Existing Customer APIs/services
* Existing Project → Customer relationship
* Existing Communications → Customer relationship
* Existing customer detail page
* Existing customer creation form
* Existing customer search
* Existing permissions
* Existing activity/audit logging
* Existing archive/delete patterns
* Existing reusable form/modal components

Do not begin by rebuilding the customer UI from scratch.

Preserve the current SiteTech design language.

---

# 2. CUSTOMER NOW REPRESENTS A COMPANY / ORGANIZATION

The primary Customer record should represent the business or organization.

Examples:

ABC Construction

XYZ Development

Smith Engineering

NJ American Water

Each Customer should support at minimum:

* Unique ID
* Company name
* Main company phone
* General email
* Website
* Address line 1
* Address line 2
* City
* State
* ZIP
* Customer type
* Status
* Notes
* Created date/time
* Updated date/time
* Created by where already supported
* Archived status

The existing company/customer information should be migrated into this structure where applicable.

---

# 3. CUSTOMER TYPE

Add a Customer Type field.

Initial options:

* General Contractor
* Developer
* Owner
* Construction Manager
* Engineer
* Architect
* Municipality / Public Agency
* Property Manager
* Vendor
* Other

For now, one primary type is sufficient.

Build the database so this could later become multiple tags/types if needed, but do not over-engineer this now.

---

# 4. CUSTOMER STATUS

Add or preserve a Customer Status field.

Use:

* Active
* Inactive
* Archived

Default new customers to Active.

Archived customers should not appear in the normal customer list unless the user intentionally includes archived customers.

---

# 5. MULTIPLE CONTACTS

Create a new Contacts entity/table.

Each Customer may have unlimited Contacts.

Each Contact should contain:

* Unique ID
* Customer ID
* First name
* Last name
* Job title
* Email
* Office phone
* Mobile phone
* Extension
* Primary contact flag
* Active / inactive status
* Notes
* Created date/time
* Updated date/time

Do not require every field.

At minimum, a Contact should require a name.

---

# 6. CONTACT ROLES

Add a separate Contact Role field.

This is different from Job Title.

Example:

Job Title:
Senior Project Manager

Contact Role:
Project Management

Initial role options:

* Estimating
* Project Management
* Purchasing
* Accounting / AP
* Executive / Owner
* Contract Signer
* Superintendent
* Engineering
* Other

Prefer allowing multiple roles per contact if this can be implemented cleanly.

Example:

John Smith

Job Title:
Vice President

Roles:

* Estimating
* Contract Signer

If multi-role support adds substantial complexity, a single role may be used initially, but architecture should not make future multi-role support difficult.

---

# 7. PRIMARY CONTACT

Allow one Contact under a Customer to be marked:

Primary Contact

Rules:

* A Customer does not have to have a Primary Contact.
* There should generally be no more than one Primary Contact.
* If a new Contact is marked Primary, remove Primary from the previous Contact.
* Do not delete the previous Contact.

Customer cards and overview screens may display the Primary Contact where useful.

---

# 8. CONTACT ACTIVE / INACTIVE

Contacts should generally not be permanently deleted once they have historical relationships.

If someone leaves a company:

John Smith
Inactive

Historical records should remain intact.

Administrators should be able to:

* Edit Contact
* Mark Contact inactive
* Reactivate Contact

Hard delete should only be allowed when appropriate and when it will not destroy meaningful history.

---

# 9. EDIT CUSTOMER

Add a clear:

Edit Customer

button to the Customer detail page.

Users with permission should be able to edit:

* Company name
* Main phone
* General email
* Website
* Customer type
* Address
* Status
* Notes

Do not require deleting/recreating a Customer just to fix information.

---

# 10. EDIT CONTACT

Each Contact should have:

* Edit
* Deactivate / Reactivate
* Delete only where appropriate

Editing a Contact should not affect unrelated historical records.

---

* Job title

---

# 14. PROJECTS TAB

Preserve the existing Projects tab and existing Customer → Project relationships.

Projects should continue to belong to the Customer/company.

Do not change Projects so that they belong directly to an individual Contact.

A Project may later have multiple Contacts associated with it separately.

Do not implement Project Contacts unless needed to preserve existing data.

---

# 15. COMMUNICATIONS TAB

Preserve and improve the current Communications functionality.

Each Communication should continue to link to the Customer.

Add optional relationships for:

* Contact
* Project

Future architecture should allow:

* Opportunity

but do not build Opportunities now.

Example Communication:

Customer:
ABC Construction

Contact:
John Smith

Project:
100 South Main Street

Type:
Phone Call

Notes:
Discussed revised excavation pricing.

---

# 16. COMMUNICATION CONTACT SELECTION

When logging a Communication:

Provide a Contact dropdown containing Contacts belonging to the selected Customer.

Do not allow selecting a Contact from an unrelated Customer.

Contact is optional because some communications may be general company communications.

---

# 17. COMMUNICATION PROJECT SELECTION

Allow optionally associating a Communication with a Project.

Only show Projects belonging to the selected Customer unless application architecture requires otherwise.

If Communication is opened from inside a Project, automatically populate:

* Customer
* Project

If opened from a Customer, automatically populate:

* Customer

---

# 18. COMMUNICATION HISTORY

Communications should remain accessible even if:

* Contact becomes inactive
* Project closes
* Customer becomes archived

Do not destroy communications when related records are deactivated.

---

# 19. SEARCH IMPROVEMENTS

Upgrade Customer search.

Searching should match:

* Company name
* Contact first name
* Contact last name
* Contact full name
* Contact email
* Contact phone
* Company email
* Company phone
* Address

Example:

Searching:

John Smith

should return:

ABC Construction

because John Smith is a Contact for ABC Construction.

The search result may display matching Contact information to explain why the Customer matched.

---

# 20. CUSTOMER LIST

Preserve the current clean Customer card/grid design.

Update cards so the main identity is the Company.

Recommended card:

ABC Construction

General Contractor

John Smith
Primary Contact

[john@abc.com](mailto:john@abc.com)
555-123-4567

If there is no Primary Contact, simply display the Company information.

Avoid making cards overly dense.

---

# 21. CUSTOMER ARCHIVING

Replace dangerous customer deletion behavior where appropriate.

Add:

Archive Customer

If a Customer has historical records such as:

* Projects
* Communications
* future Opportunities
* future Proposals
* future Contracts

do not allow normal users to permanently delete it.

Instead:

Status = Archived

Archived customers should:

* Retain all history
* Retain Projects
* Retain Communications
* Not appear in default active Customer list

Provide filter:

Active
Inactive
Archived
All

---

# 22. HARD DELETE

Hard delete should only be allowed for administrators and preferably only if:

* Customer has no Projects
* No Communications
* No important related records
* No historical dependencies

If deletion would break historical relationships, prevent it and explain why.

Example:

"This customer cannot be deleted because it has 4 Projects and 7 Communications. Archive the customer instead."

---

# 23. DUPLICATE CUSTOMER WARNING

Add lightweight duplicate detection during Customer creation.

If the entered Company name is similar to an existing Customer, display a warning.

Example:

Possible existing customer:

ABC Construction LLC

[View Customer]

Still allow creation if the user confirms.

Do not automatically merge customers.

---

# 24. DUPLICATE CONTACT WARNING

If adding a Contact whose email already exists under the same Customer, warn the user.

Do not automatically merge Contacts.

---

# 25. CUSTOMER NOTES

Keep a general Notes field on the Customer.

Use it for persistent company-level information.

Examples:

Requires COI before mobilization.

Send all invoices to [accounting@abc.com](mailto:accounting@abc.com).

Do not use Customer Notes as an activity timeline.

Ongoing events belong in:

* Communications
* Activity

---

# 26. CONTACT NOTES

Allow optional Notes on individual Contacts.

Examples:

Prefers text messages.

Handles sitework estimates only.

Do not mix Contact Notes with Communications history.

---

# 27. ACTIVITY LOG

Integrate with the existing SiteTech activity/audit system.

Record meaningful events such as:

* Customer created
* Customer edited
* Customer archived
* Contact added
* Contact edited
* Contact deactivated
* Contact reactivated
* Primary Contact changed
* Communication logged

Use the existing Activity system.

Do not create a second activity log.

---

# 28. PERMISSIONS

Use the existing SiteTech authentication and permission system.

Server-side authorization is required.

Users should only be able to:

* Create Customers
* Edit Customers
* Add Contacts
* Edit Contacts
* Archive Customers

if their existing permissions allow it.

Do not create a separate permission system specifically for Customers.

Existing SiteTech Customer records already contain data.

Before migrating:

Inspect exactly how the existing Customer table stores:

* Contact name
* Company
* Email

* Address

555-1234

---

# 31. EXISTING RECORDS WITHOUT COMPANY NAME

Some existing Customers may have only a Contact Name and no Company.

Do not lose these records.

Use a sensible migration approach.

For example:

Customer Name:
John Smith

Contact:
John Smith

Do not invent a fake company.

Flag these records if useful so they can later be cleaned up manually.

---

# 32. EXISTING PROJECT LINKS

This is critical.

All existing Project → Customer links must continue working after migration.

Do not:

* recreate Projects
* duplicate Projects
* change Project IDs
* orphan Projects

Test every migrated Customer relationship.

---

# 33. EXISTING COMMUNICATION LINKS

Existing Communications must remain attached to the correct Customer.

Do not create duplicate Communications.

If existing Communication records cannot automatically identify a Contact, leave Contact blank.

Do not guess which Contact participated.

# COMPLETION CRITERIA

This feature is complete when:

* A Customer represents a Company/organization.
* A Customer can have multiple Contacts.
* Contacts support job titles and roles.
* One Contact can be Primary.
* Contacts can be edited and deactivated.
* Customers can be edited.
* Customers can be archived instead of destroying history.
* Existing Projects remain connected correctly.
* Existing Communications remain connected correctly.
* Communications can optionally identify a Contact and Project.
* Customer search includes Contacts.
* Existing Customer data has been safely migrated.
* Activity logging works.
* Mobile UI remains clean.
* Existing SiteTech functionality is not broken.

---

# FINAL INSTRUCTION

This is an upgrade to an existing production data structure.

Preserving existing data and relationships is more important than implementing the feature quickly.

Before applying destructive database changes, inspect the existing schema and produce a safe migration strategy.

Do not delete, duplicate, or recreate existing Projects or Communications.

Extend the current Customer system rather than creating a parallel replacement.

The purpose of this upgrade is to establish the correct Customer → Contact foundation for the upcoming SiteTech Opportunity, RFP, estimating, proposal, and contract systems.
