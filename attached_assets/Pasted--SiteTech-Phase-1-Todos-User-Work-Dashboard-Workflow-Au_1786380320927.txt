# SiteTech Phase 1 — Todos, User Work Dashboard, Workflow Automation, Notifications & Activity Log

We are expanding the existing **SiteTech construction management application**.

This is an existing production application with current users, projects, project statuses, tasks, daily reports, documents, photos, equipment, scheduling, and other functionality.

Before making changes, inspect the existing application architecture, database schema, authentication/user system, project structure, navigation, styling patterns, email/notification functionality, and existing reusable components.

## Important Development Rules

1. Do not rebuild functionality that already exists.
2. Reuse the existing User and Project records.
3. Do not create duplicate user, project, or authentication systems.
4. Follow the existing application design and coding patterns where practical.
5. Make all database changes through proper migrations.
6. Do not break existing functionality.
7. Maintain existing data.
8. Design this system so future modules such as RFPs, Estimates, Proposals, Change Orders, T&M Tickets, Submittals, RFIs, Inspections, and other records can use the same Todo and workflow infrastructure.
9. Do not hard-code specific users, IDs, project names, or workflow assignments.
10. The application must remain fully usable on desktop and mobile.
11. Mobile pages must fit the viewport without horizontal scrolling.
12. Use clear, light, professional construction-management UI consistent with the existing SiteTech application.

---

# PHASE 1 GOAL

Create a centralized **Action / Todo Management System** for SiteTech.

Users should be able to:

* Create todos manually.
* Assign todos to other SiteTech users.
* Associate todos with projects.
* Assign due dates.
* Set priority.
* Track completion.
* View all work assigned to them from a central dashboard.
* Automatically receive todos when project statuses change based on configurable workflow rules.
* Receive notifications when relevant actions occur.
* Maintain a reliable audit/history record of important actions.

The Todo system must be designed as a reusable platform feature rather than something that only works for Projects.

# 1. UNIVERSAL TODO SYSTEM

Create a centralized Todo / Action Item system.

## Todo Data Model

Each Todo should support at minimum:

* Unique ID
* Title
* Description / notes
* Assigned user
* Created by user
* Project
* Due date
* Priority
* Status
* Created date/time
* Updated date/time
* Completed date/time
* Completed by user
* Source / related record
* Whether the todo was manually created or automatically generated
* Workflow rule that generated it, if applicable

### Todo Statuses

Use:

* Open
* In Progress

Make the status architecture easy to expand later.

### Priority

Use:

* Low
* Normal
* High
* Urgent

# 2. GENERIC RECORD LINKING

Do NOT design Todos so they can only belong to a Project.

A Todo may be associated with a Project while also relating to another application record.

Examples:

* Project
* Future RFP
* Future Estimate
* Future Proposal
* Future Change Order
* Future T&M Ticket
* Future Submittal
* Future RFI
* Future Inspection

Build the architecture now so additional record types can be added without redesigning the Todo system.

For example, use a generic relationship concept similar to:

* relatedEntityType
* relatedEntityId

or another appropriate polymorphic/reference architecture that fits the existing database and application.

A Todo should still have a direct Project relationship whenever a Project is known because project-based filtering will be heavily used.

Do not create fake placeholder tables for future modules. Simply make the Todo architecture capable of linking to them later.

* Send notification
* Send email

# 13. GLOBAL PROJECT STATUS RESPONSIBILITY

An administrator should be able to configure a default responsible user for each Project Status.

Example:

RFP Received → User A
Pricing → User B
Proposal Ready → User C
Awarded → User D

When a Project enters that status, the configured workflow should run.

However, design this using workflow rules rather than permanently hard-coding responsibility into Project Status itself if the workflow architecture provides greater flexibility.

The admin interface should make this simple enough that a nontechnical SiteTech administrator can configure it.

---

# 14. WORKFLOW DUE DATE OFFSETS

Workflow-generated Todos should allow the administrator to specify:

* Due immediately
* Due in X calendar days
* No due date

Build the data model so support for **business days** can be added later, but business-day calculation is not required in this version unless it can be implemented cleanly.

---

# 15. PREVENT DUPLICATE AUTOMATION

This is important.

Changing a Project Status should not accidentally create duplicate automated Todos because:

* the page was refreshed,
* an API request retried,
* a user saved the same status again,
* or an event handler fired twice.

Workflow execution must be idempotent where appropriate.

Record each workflow execution.

For example maintain:

* Workflow Rule ID
* Project ID
* Trigger event
* Status transition
* Execution date/time
* Generated Todo ID

This provides both duplicate protection and an audit trail.

---

# 16. STATUS TRANSITIONS

A workflow should trigger when a Project actually **changes from one status to another**.

Do not trigger simply because the Project is saved while already having that status.

Example:

Pricing → Proposal Ready

should trigger Proposal Ready workflows.

Editing the Project address while status remains Proposal Ready should NOT trigger the workflow again.

# 22. DUE DATE NOTIFICATIONS

For this phase, the My Work dashboard must clearly identify overdue and due-today Todos.

Build the notification architecture so scheduled reminders can later support things such as:

* Todo due tomorrow
* Todo due today
* Todo overdue

Do not build an unnecessarily complicated scheduler if this infrastructure does not already exist.

If scheduled reminders can be implemented cleanly with the existing architecture, add:

* Due today in-app notification once per Todo
* Overdue notification once when the Todo first becomes overdue

Make sure repeated background jobs do not generate duplicate notifications.

# 27. DATA INTEGRITY

Important requirements:

* Deleting a Project should not cause invalid Todo records.
* Deleting/deactivating a User should not destroy historical activity.
* Completed Todo history must remain available.
* Workflow execution history must remain available.
* Activity records should not disappear merely because a Todo is completed.
* Avoid cascade deletes that would destroy important project history.

Follow the application's current archival/deletion strategy where possible.

---

# 28. USER DEACTIVATION

If an assigned user becomes inactive:

* Existing Todos must remain visible historically.
* Administrators must be able to reassign open Todos.
* Workflow rules assigned to inactive users should display a clear warning.

Do not silently assign work to an inactive user.

# 30. PERFORMANCE

Queries must be efficient.

Do not load all application Todos and filter them only in the browser.

My Work should retrieve only relevant records from the server/database.

Use pagination or sensible result limiting if lists become large.

Avoid unnecessary repeated requests.

Ensure dashboard counts and Todo lists remain responsive as thousands of Todos accumulate.

---

# 31. SECURITY

All Todo, workflow, notification, and activity APIs must require authentication.

Apply server-side authorization.

A user should not gain access to a Project simply because they know a Todo ID.

Use existing Project access rules where applicable.

Sanitize user-entered text.

Validate all IDs and relationships server-side.

7. Notification is created.
8. Email is sent if enabled.

10. Workflow execution is recorded.

1. Save Project without changing status.
2. No additional Todo should be created.
3. Refresh page.

Test:

* My Work

* Edit Todo

at common phone widths.

# 40. COMPLETION CRITERIA

This phase should not be considered complete until:

* Users can manually assign Todos.
* Todos can have projects, due dates, priorities, and statuses.
* Users have a My Work dashboard.
* Overdue and due-today work is obvious.
* Project pages show their Todos.
* Todos can be completed without deleting history.
* Admins can create Project Status workflow rules.
* Changing a Project Status can automatically assign work.
* Workflow Todos do not duplicate accidentally.
* Users receive in-app notifications.
* Workflow emails work when enabled.
* Status transitions are historically recorded.
* Important actions appear in an audit/activity log.
* Permissions are enforced server-side.
* Mobile UI works cleanly.
* Existing SiteTech features continue functioning.

# FINAL INSTRUCTION

Do not begin by making broad visual changes.

Start by inspecting the existing SiteTech application and identifying how this feature should integrate into the existing architecture.

Preserve current functionality.

Where an existing feature or database concept overlaps these requirements, extend it instead of creating a duplicate.

If implementation reveals an architectural conflict with the existing application, choose the approach that maintains one clean source of truth and document the decision in the code/comments as appropriate.

The goal of this phase is not merely to add a Todo page.

The goal is to create the reusable **workflow and action-management foundation for the future SiteTech construction-management platform**.
