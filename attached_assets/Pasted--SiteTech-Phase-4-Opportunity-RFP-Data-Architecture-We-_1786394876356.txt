# SiteTech — Phase 4: Opportunity / RFP Data Architecture

We are continuing development of the existing SiteTech construction-management application.

The following foundation already exists:

* Users and authentication
* Projects
* Customers / Companies
* Multiple Contacts under Customers
* Todos / My Work
* Workflow automation
* Notifications
* Email infrastructure
* Activity / audit logging
* Communications

The next major feature is the **Opportunity / RFP / Bidding system**.

This phase is focused primarily on creating the correct **database architecture, backend services, relationships, permissions, status model, and basic CRUD foundation**.

Do NOT build the full visual bidding pipeline/dashboard yet. That will be the next phase.

---

# 1. PRIMARY GOAL

Create a new core entity called:

# Opportunity

An Opportunity represents a potential SiteTech project that is being evaluated, estimated, bid, negotiated, won, lost, or declined.

Examples:

* Sitework RFP received from a GC
* Invitation to bid on a project
* Customer asks SiteTech for excavation pricing
* Existing customer asks for preliminary budget pricing
* Negotiated project opportunity
* Private project being evaluated before a formal proposal

An Opportunity should exist independently from an active Project.

Do NOT create a Project simply because an RFP is received.

A Project should eventually be created when an Opportunity is awarded.

---

# 2. TERMINOLOGY

Use:

**Opportunity**

as the core technical/database entity.

Future UI may use terminology such as:

* Bidding
* Opportunities
* RFPs

Do not name the core data model only "RFP" because not every opportunity will necessarily originate from a formal RFP.

---

# 3. OPPORTUNITY LIFECYCLE

The architecture should support a lifecycle similar to:

New / RFP Received
→ Under Review
→ Estimating
→ Proposal Ready
→ Proposal Sent
→ Follow-Up / Negotiation
→ Awarded

or:

→ Lost

or:

→ No Bid / Declined

or:

→ On Hold

Create the following initial statuses:

* New
* Under Review
* Estimating
* Proposal Ready
* Proposal Sent
* Follow-Up
* On Hold
* Awarded
* Lost
* No Bid

Do not hard-code business logic throughout the application based on text labels.

Use stable IDs, enums, status records, or another clean architecture consistent with the existing application.

The status architecture should be expandable later.

---

# 4. LOST VS NO BID

Treat these as different outcomes.

## Lost

SiteTech submitted or pursued the opportunity but did not receive the project.

## No Bid

SiteTech deliberately chose not to submit pricing.

This distinction is important for future reporting.

Examples:

Lost:
"We submitted $750,000 but another contractor was selected."

No Bid:
"Schedule is too aggressive; we decided not to price."

---

# 5. OPPORTUNITY DATA MODEL

Each Opportunity should support at minimum:

* Unique ID
* Opportunity number
* Opportunity name / project name
* Customer / Company
* Primary contact if selected
* Opportunity status
* Estimator / responsible SiteTech user
* Project address
* Address line 2
* City
* State
* ZIP
* RFP received date
* Bid due date
* Bid due time
* Estimated project start date
* Opportunity source
* Project type
* Scope summary
* Internal notes
* Expected / preliminary value if known
* Probability / confidence if used
* Lost reason
* No Bid reason
* Award date
* Created by
* Created date/time
* Updated date/time
* Archived status if needed

Do not require every field.

The minimum required information should preferably be:

* Opportunity name
* Customer
* Status

Other information can be added as it becomes known.

---

# 6. OPPORTUNITY NUMBER

Every Opportunity should receive a unique human-readable Opportunity number.

Example:

OPP-2026-0012

or another format consistent with SiteTech.

Requirements:

* Unique
* Automatically generated
* Cannot accidentally duplicate
* Should not depend only on client-side logic
* Should remain unchanged even if project name changes

Do not reuse Project IDs as Opportunity numbers.

Build numbering so the format could be changed later without changing primary database IDs.

---

# 7. CUSTOMER RELATIONSHIP

Each Opportunity should normally belong to one Customer / Company from the existing Customer database.

Use the existing Customer entity.

Do NOT create duplicate customer/company records inside the Opportunity module.

Example:

Customer:
ABC Construction

Opportunity:
100 South Main Street Sitework

---

# 8. MULTIPLE CONTACTS PER OPPORTUNITY

An Opportunity may involve multiple Contacts from the selected Customer.

Example:

ABC Construction

Opportunity Contacts:

John Smith
Estimator

Mike Jones
Project Executive

David Brown
Contract Signer

Create an Opportunity ↔ Contact relationship capable of supporting multiple contacts.

Conceptually:

OPPORTUNITY_CONTACTS

* opportunity_id
* contact_id
* opportunity_role
* is_primary
* timestamps if appropriate

Do not duplicate Contact information into the Opportunity table except where a historical snapshot is later specifically required.

---

# 9. OPPORTUNITY CONTACT ROLE

The same Contact may serve different purposes on different Opportunities.

Support an optional Opportunity-specific role such as:

* Estimator
* Project Manager
* Project Executive
* Superintendent
* Purchasing
* Accounting
* Contract Signer
* Owner
* Other

Do not confuse this with the Contact's general company-level job title or Contact Role.

Example:

John Smith

Company Job Title:
Vice President

Company Roles:
Estimating, Executive

Opportunity Role:
Estimator

---

# 10. PRIMARY OPPORTUNITY CONTACT

Allow one Contact to be designated:

Primary Opportunity Contact

This does not change the Customer's overall Primary Contact.

Example:

ABC Construction's company-level primary Contact may be the owner.

But for this particular bid, John the estimator may be the Primary Opportunity Contact.

Keep those concepts separate.

---

# 11. PROJECT ADDRESS

The Opportunity project address must be independent from the Customer's office address.

Do not copy the Customer address into the Opportunity automatically unless the user intentionally chooses it.

Store structured fields:

* Address
* Address line 2
* City
* State
* ZIP

Architecture should allow coordinates/geolocation later if needed.

---

Initial options might include:

* Existing Customer
* Invitation to Bid
* Email RFP
* Referral
* Website / Inbound

* Developer / Owner
* Public Bid
* Other

Make this configurable or expandable where practical.

This will eventually allow reporting such as:

"Where are our successful opportunities coming from?"

---

# 13. PROJECT TYPE

Add a Project Type field.

Initial examples:

* Commercial
* Multifamily
* Residential
* Industrial
* Institutional
* Municipal / Public
* Infrastructure
* Mixed Use
* Other

Avoid excessive complexity initially.

# 14. SCOPE SUMMARY

Provide an Opportunity-level Scope Summary text field.

Example:

Site clearing, foundation excavation, sanitary sewer, water service, stormwater system and final grading.

This is only a high-level summary.

Do NOT build the detailed Scope/Pricing Checklist in this phase.

That is a future step.

---

# 15. INTERNAL NOTES

Add an Internal Notes field for general Opportunity-level information.

Examples:

Customer wants VE option for stormwater.

Plans appear incomplete.

Need trucking prices before committing to bid.

Do not use this field as a chronological activity log.

Ongoing events should be recorded through:

* Communications
* Activity
* Todos

---

# 16. BID DUE DATE AND TIME

Support:

* Bid due date
* Bid due time

Time should be optional.

Examples:

August 21, 2026
2:00 PM

Do not store only a formatted text string.

Use proper date/time fields.

Respect the application's timezone conventions.

---

# 17. RFP RECEIVED DATE

Store when the opportunity/RFP was received.

This will later support reporting such as:

* Average days from RFP received to bid submission
* Number of bids received per month

This may default to today's date when an Opportunity is created but should remain editable.

---

# 18. ESTIMATED START DATE

Allow an optional estimated project start date.

This is preliminary and does not become the actual Project schedule automatically.

---

# 19. ESTIMATOR / RESPONSIBLE USER

Each Opportunity should support a responsible SiteTech user.

Examples:

Estimator
Preconstruction Manager
Owner handling the bid

Use the existing User system.

Do not create a separate estimator table.

The responsible user should be changeable.

---

# 20. WORKFLOW ENGINE INTEGRATION

Use the existing SiteTech Workflow Automation system.

Opportunity statuses must be designed so they can trigger workflow rules.

Future examples:

Opportunity created
→ Assign estimator
→ Create Todo

Status changes to Estimating
→ Create "Complete estimate" Todo

Status changes to Proposal Sent
→ Create follow-up Todo due in 5 days

Status changes to Awarded
→ Notify management

Do not hard-code these automations directly into the Opportunity module if the existing generic Workflow system can handle them.

Extend the Workflow system so Opportunity status changes can be a trigger type.

---

# 21. TODOS

Use the existing universal Todo system.

Todos should be able to link to:

* Opportunity
* Customer
* Future Estimate
* Future Proposal

For this phase, ensure Todo generic entity linking supports Opportunity records.

Example:

Todo:
Review RFP documents

Project:
None

Related Entity:
Opportunity #OPP-2026-0012

This is important because the Opportunity may not yet have a Project.

---

# 22. MY WORK

Do not create a separate opportunity task system.

Example:

Review RFP documents

Opportunity:
100 South Main Street

Due:
Aug 13

# 32. AWARDED STATUS

converted_project_id

# 33. FUTURE CONVERSION TO PROJECT

* Opportunity name

* Award information
* Proposal/contract

Do not duplicate all historical data into the Project unnecessarily.

# 35. NO BID

When status becomes No Bid, support:

No Bid reason

Suggested options:

* Outside Scope
* Insufficient Time

---

# 36. LOST / NO BID HISTORY

Lost and No Bid Opportunities should remain searchable and reportable.

Do not delete them.

They represent valuable business history.

---

# 37. ARCHIVING

Awarded, Lost, and No Bid are business statuses.

Archive is different.

Archiving should simply hide old records from default views without destroying them.

Do not automatically archive immediately when an Opportunity becomes Lost or Awarded.

---

# 38. PERMISSIONS

Use the existing SiteTech permission system.

Design permissions around abilities such as:

* View Opportunities
* Create Opportunities
* Edit Opportunities
* Change Opportunity Status
* Assign Opportunity Responsible User
* View Financial/Expected Value fields if needed
* Archive Opportunities

Do not create an entirely separate authentication system.

All authorization must be enforced server-side.

---

# 39. DATA ACCESS SECURITY

A user should not be able to access an Opportunity just by knowing its ID.

Respect existing organization/account/project access patterns.

Validate:

* User authentication
* Customer existence
* Contact belongs to Customer
* Responsible user is valid
* Opportunity status is valid
* Related IDs are valid

---

# 40. CUSTOMER CONTACT VALIDATION

If Customer is:

ABC Construction

the user should not be able to assign a Contact belonging to:

XYZ Development

as an Opportunity Contact.

Enforce this server-side.

If Customer changes, existing Opportunity Contacts that no longer belong to the selected Customer must be handled safely.

Do not silently retain invalid relationships.

---

# 41. CUSTOMER CHANGE

If the user changes the Customer after creating an Opportunity:

Warn them if Contacts, Communications, or related records already reference the previous Customer.

Do not automatically delete historical data.

Use a safe strategy consistent with existing data-integrity patterns.

* Create Opportunity
* Read Opportunity
* Update Opportunity

* Assign responsible user

---

# 47. API / SERVICE ARCHITECTURE

Do not place all business logic directly in frontend components.

Use the existing SiteTech application structure.

Centralize important logic such as:

* Opportunity number generation
* Status transition handling
* Workflow triggering
* Activity logging
* Status history
* Customer/contact validation

This prevents different screens from handling status changes differently.

---

# 48. STATUS CHANGE SERVICE

Opportunity status changes should run through one centralized backend/service method.

That method should:

1. Validate permission
2. Validate new status
3. Compare old vs new status
4. Update status
5. Record status history
6. Record activity
7. Trigger applicable workflows
8. Return updated Opportunity

Do not scatter this behavior across UI pages.

---

# 49. WORKFLOW DUPLICATE PREVENTION

Use the duplicate/idempotency protection already implemented in the Workflow system.

Changing:

Estimating → Proposal Ready

should trigger Proposal Ready workflow once.

Saving Proposal Ready → Proposal Ready should not trigger another workflow.

# COMPLETION CRITERIA

This phase is complete when:

* Opportunity exists as a separate entity from Project.
* Opportunities link to existing Customers.
* Opportunities support multiple Contacts.
* Opportunity-specific Contact roles work.
* Opportunity numbers are generated safely.
* Opportunity statuses and status history work.
* Responsible users can be assigned.
* Bid dates and basic RFP information can be stored.
* Lost and No Bid reasons can be recorded.
* Todos can link to Opportunities.
* My Work supports Opportunity-linked Todos.
* Communications can link to Opportunities.
* Activity logging works.
* Workflow automation can respond to Opportunity status changes.
* Existing SiteTech functionality remains intact.
* Architecture supports future Takeoffs, Estimates, Proposals and Project conversion.

---

# FINAL INSTRUCTION

Before implementing database changes, inspect the existing SiteTech codebase and database.

Pay particular attention to how current Projects with statuses such as "new" or "bidding" are being used.

Do not destroy or automatically migrate existing Projects.

This phase should establish a clean distinction:

Opportunity = work SiteTech is pursuing

Project = work SiteTech has actually been awarded / is managing

Build the Opportunity foundation as reusable production architecture, not as a temporary screen that will need to be replaced when estimating and proposals are added.
